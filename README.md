# Ory auth stack

Drop-in auth for side projects: [Ory Kratos](https://www.ory.sh/kratos/) handles logins, [Ory Oathkeeper](https://www.ory.sh/oathkeeper/) sits in front of your services, and a small Rust **user-service** owns user data (profile, roles). **Your services are stateless.** They never see sessions; every request carries a short-lived signed JWT that already contains the user's profile and roles.

```
browser ──cookie──▶ Oathkeeper :8080 ──Authorization: Bearer <JWT>──▶ your services
                        │ 1. "who owns this session?"   → Kratos :4433 (email, login state)
                        │ 2. "who is this user?"        → user-service :3001 (profile, roles)
                        │ 3. mint JWT from 1 + 2
                     Kratos ◀── login/registration/settings UI :4455
```

**What you get:** email + password sign-up, passwordless email codes, passkeys, Google and GitHub login, email verification, account recovery, and optional 2FA (TOTP and backup codes). It all comes with ready-made UI pages.

```bash
just up        # first run: generates .env secrets + JWT signing key, then starts everything
```

| URL | What |
| --- | --- |
| http://localhost:8080 | **Your app**, through Oathkeeper (placeholder echo service until you plug yours in) |
| http://localhost:4455 | Login / registration / settings / logout UI |
| http://localhost:8025 | Mailpit: every email Kratos sends lands here |
| http://localhost:4433 | Kratos public API |
| http://localhost:4434 | Kratos admin API (127.0.0.1 only) |
| http://localhost:4456 | Oathkeeper API: JWKS at `/.well-known/jwks.json` (127.0.0.1 only) |

Run `just` to list the commands: `up`, `down`, `restart`, `logs [service...]`, `ps`, `test`, `jwt EMAIL PASSWORD`, and `reset` (**deletes all users**, asks first). There are also user-admin and database commands; see [Administration](#administration).

> Always use `localhost`, not `127.0.0.1`. Cookies are per host, and passkeys don't work on IP addresses.

## Layout

```
docker-compose.yml               postgres, kratos (+ migrate), kratos-ui, mailpit, oathkeeper, user-service (+ migrate), app (placeholder)
kratos/kratos.yml                Kratos: URLs, login methods, flows
kratos/identity.schema.json      identity fields ("traits"): email only, the login identifier
kratos/entrypoint.sh             turns GOOGLE_*/GITHUB_* env vars into social-login config
kratos/oidc/*.jsonnet            maps Google/GitHub profile data to user traits
oathkeeper/oathkeeper.yml        Oathkeeper: auth handlers, JWT claims, error handling
oathkeeper/access-rules.yml      routes: what's public, what needs login, where to forward
oathkeeper/id_token.jwks.json    JWT signing key (generated by `just init`, gitignored)
postgres/create-users-db.sql     creates user-service's own role + database in the shared Postgres
user-service/                    Rust (axum + sqlx): user data, the hydrator, /api/users/me
  migrations/                    reversible sqlx migrations (*.up.sql / *.down.sql)
  .sqlx/                         offline query data for the Docker build (`just sqlx-prepare`)
```

## Routes

Defined in `oathkeeper/access-rules.yml`, which reloads live without a restart. A request that matches no rule gets a **404**, so the default is deny.

| Path | Requires | Without login | Your app receives |
| --- | --- | --- | --- |
| `/`, `/public/**` | nothing | passes through | no JWT |
| `/app`, `/app/**` | browser session | 302 to login, then back | JWT |
| `/api/app/**` | browser session **or** `Authorization: Bearer <kratos session token>` | 401 JSON | JWT |
| `/api/users/**` | same | 401 JSON | user-service gets the JWT |

Rules must not overlap (Oathkeeper rejects a request that matches two), so give each service its own prefix: `/api/<service>/**`.

On every route, Oathkeeper blanks the `ory_kratos_session` cookie before forwarding, so the session credential never reaches your app.

## Plugging in your app

1. Replace the `app` service in `docker-compose.yml` with yours. Don't publish its port: everything must go through Oathkeeper.
2. Point the `upstream.url`s in `access-rules.yml` at it, and adjust the paths. Keep the mutator order `hydrator`, `id_token`, `cookie` on logged-in rules.
3. In the app, verify the `Authorization: Bearer` JWT on every protected route. `user-service/src/auth.rs` is a complete Rust example (JWKS fetch + cache + key rotation, tests with a fixed test key).

### The JWT contract

| | |
| --- | --- |
| Algorithm | `EdDSA` (Ed25519). **Pin it**: never accept the `alg` the token names. |
| Keys | `http://oathkeeper:4456/.well-known/jwks.json` (from inside compose). Match on `kid`. |
| `iss` | `http://localhost:8080/` |
| `sub` | Kratos identity id (UUID). This is your user id. |
| `exp` | 1 minute. A fresh token is minted for every request. |
| `email`, `aal` | from Kratos: login email, assurance level (`aal2` = passed 2FA) |
| `display_name`, `roles` | from user-service, added by the hydrator on every request (`roles` ⊆ `["admin", "user"]`) |

The claims are mapped in `oathkeeper.yml` → `mutators.id_token.config.claims`. A role or profile change shows up in the very next request's JWT.

To see a real one: register at http://localhost:4455, then run `just jwt you@example.com yourpassword`.

### Verifying it

All three snippets were tested against tokens from this stack. In each, `verify` accepts the key as a parameter, so tests can pass their own.

<details><summary><b>Python</b> (<code>pip install "pyjwt[crypto]"</code>)</summary>

```python
import jwt

jwks = jwt.PyJWKClient("http://oathkeeper:4456/.well-known/jwks.json")  # caches keys

def verify(token: str, key=None) -> dict:
    key = key or jwks.get_signing_key_from_jwt(token)
    return jwt.decode(token, key, algorithms=["EdDSA"], issuer="http://localhost:8080/",
                      options={"require": ["exp", "iss", "sub"]})
```
</details>

<details><summary><b>Go</b> (<code>golang-jwt/jwt/v5</code> + <code>MicahParks/keyfunc/v3</code>)</summary>

```go
type Claims struct {
	Email string   `json:"email"`
	Roles []string `json:"roles"`
	jwt.RegisteredClaims
}

// at startup (refreshes keys in the background):
jwks, err := keyfunc.NewDefaultCtx(ctx, []string{"http://oathkeeper:4456/.well-known/jwks.json"})

func verify(raw string, kf jwt.Keyfunc) (*Claims, error) {
	c := &Claims{}
	_, err := jwt.ParseWithClaims(raw, c, kf,
		jwt.WithValidMethods([]string{"EdDSA"}), jwt.WithIssuer("http://localhost:8080/"), jwt.WithExpirationRequired())
	return c, err
}
// verify(token, jwks.Keyfunc)
```
</details>

<details><summary><b>Rust</b> (<code>jsonwebtoken = { version = "11", features = ["rust_crypto"] }</code>; see <code>user-service/src/auth.rs</code> for the full version)</summary>

```rust
use jsonwebtoken::{decode, decode_header, jwk::JwkSet, Algorithm, DecodingKey, Validation};

#[derive(serde::Deserialize)]
struct Claims { sub: String, email: Option<String>, #[serde(default)] roles: Vec<String> }

// fetch JwkSet once from http://oathkeeper:4456/.well-known/jwks.json, refetch on unknown kid
fn verify(token: &str, jwks: &JwkSet) -> Result<Claims, Box<dyn std::error::Error>> {
    let kid = decode_header(token)?.kid.ok_or("no kid")?;
    let jwk = jwks.find(&kid).ok_or("unknown kid")?;
    let mut v = Validation::new(Algorithm::EdDSA);
    v.set_issuer(&["http://localhost:8080/"]);
    v.set_required_spec_claims(&["exp", "iss", "sub"]);
    Ok(decode::<Claims>(token, &DecodingKey::from_jwk(jwk)?, &v)?.claims)
}
```
</details>

### Testing with fake tokens

No Ory needed in tests. Generate an Ed25519 key pair in the test, sign whatever claims you want, and give the public key to `verify`:

```python
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
key = Ed25519PrivateKey.generate()
token = jwt.encode({"sub": "user-1", "iss": "http://localhost:8080/", "exp": int(time.time()) + 60,
                    "roles": ["admin"]}, key, algorithm="EdDSA")
verify(token, key.public_key())  # -> claims
```
(Go: `ed25519.GenerateKey` + `jwt.SigningMethodEdDSA`. Rust: `EncodingKey::from_ed_der`.)

### Where user data lives

```
Kratos (identity)              user-service DB (users)              other services' DBs
  id = 8aaf…                     users: id = 8aaf…, email (copy),     user_id = 8aaf…
  traits: email                         display_name, timestamps      (= JWT sub)
  state: active | inactive       user_roles: admin | user
            │                              │
            └──────── JWT { sub, email, display_name, roles, aal } ──→ every service
```

- **Kratos owns identity only:** the email (login identifier, verification, recovery), credentials, and whether the account may log in at all (`state`; `just deactivate` blocks every session at once). No profile data.
- **user-service owns the user:** profile fields and roles, in its own database. It creates a user's row on their first request (the hydrator), with the `user` role. No sync job, no registration webhook.
- **Other services own their own data**, keyed by `sub`, and read the profile from the JWT instead of calling user-service.
- **The JWT carries what most requests need:** small, slow-changing facts. Data only one service cares about (invoices, settings) stays a lookup in that service.
- **Deletes:** `just delete-user` removes the Kratos identity, then the user-service data (in that order, so a late request can't re-create the row). Kratos emits no "user deleted" event, so other services must clean up themselves.

### Login, logout, account links

- **Log in:** `http://localhost:4433/self-service/login/browser?return_to=http://localhost:8080/app`. Going to any `/app/**` page while logged out does this automatically.
- **Sign up:** the same URL with `registration` in place of `login`.
- **Log out / settings:** http://localhost:4455 (has a logout link) and http://localhost:4455/settings.
- **CLI or mobile clients:** use Kratos's API flows (`/self-service/login/api`) to get a session token, then send it as `Authorization: Bearer` to `/api/**` routes. `just jwt` shows the whole flow.

Every `return_to` must be listed in `selfservice.allowed_return_urls` in `kratos/kratos.yml`.

**CSRF:** Oathkeeper turns the cookie into a JWT, so cross-site requests matter. The Kratos cookie is `SameSite=Lax`, so other sites can't make POST/PUT/DELETE requests with it, but GET requests from links still carry it. **Keep GET handlers side-effect free.**

## Administration

**Users:** identity commands go to Kratos (`scripts/admin.py`, Python standard library only); role commands go to user-service's own CLI inside its container.

```bash
just users                                       # list everyone (Kratos)
just user me@x.com                               # full Kratos record + active session count
just add-user me@x.com 'S3cret-pass!'            # create a pre-verified user (dev seeding)
just grant-role me@x.com admin                   # roles: admin, user; in the JWT from the next request
just revoke-role me@x.com admin
just revoke me@x.com                             # log out everywhere
just deactivate me@x.com                         # block: sessions stop working at once, login refused
just activate me@x.com                           # unblock (suspended sessions work again)
just recover me@x.com                            # one-hour recovery link + code to send them
just delete-user me@x.com                        # Kratos identity + user-service data; asks first
```

The role and delete commands look the email up in Kratos and then act on the identity id, never on user-service's copy of the email (it isn't unique, and it's only refreshed when the user makes a request). So `grant-role` also works for users who registered but never made a request yet. It needs no admin API, so it also bootstraps the first admin. If the Kratos identity is already gone, remove leftover data by id: `docker compose exec user-service /user-service forget-user <id>`.

**Database** (user-service): migrations are reversible sqlx pairs in `user-service/migrations/`, compiled into the binary. On every `just up`, the one-shot `user-service-migrate` service (same image, `user-service migrate`) applies pending ones and exits; user-service only starts after it succeeds, and never migrates itself.

```bash
just migration add_avatar_url    # new user-service/migrations/0003_add_avatar_url.{up,down}.sql
just migrate                     # apply pending migrations to the dev database
just migrate-revert              # run the latest .down.sql (asks first)
just sqlx-prepare                # after changing any query: refresh .sqlx/ (the Docker build needs it)
just test                        # all user-service tests, each DB test in a throwaway database
```

Queries use sqlx's compile-time-checked macros, so a wrong column or type is a compile error. Locally they check against the dev database (`user-service/.env`, gitignored); the Docker build uses the committed `.sqlx/` instead.

For anything else, use the admin API directly ([reference](https://www.ory.sh/docs/kratos/reference/api)), the official SDKs (Go/Python/Rust `ory-client`), or the Kratos CLI: `docker compose exec kratos kratos list identities -e http://localhost:4434`.

**Routing** (Oathkeeper): it stores nothing, so the config files in git are all there is. Edit `oathkeeper/access-rules.yml` (reloads live) or `oathkeeper.yml` (then `just restart`). To debug, `curl localhost:4456/rules` lists the loaded rules, and `just logs oathkeeper` shows each allow/deny decision.

## Social login

Fill in the vars in `.env`, then run `just restart`. A provider shows up only when both its ID and secret are set.

- **GitHub:** https://github.com/settings/developers → *New OAuth App*
  Callback URL: `http://localhost:4433/self-service/methods/oidc/callback/github`
- **Google:** https://console.cloud.google.com/apis/credentials → *OAuth client ID* → *Web application*
  Authorized redirect URI: `http://localhost:4433/self-service/methods/oidc/callback/google`

To add another provider (Discord, Microsoft, Apple, GitLab, …), add one `add_provider` line in `kratos/entrypoint.sh`, add a mapper in `kratos/oidc/`, and pass its env vars to the `kratos` service.

## Customizing

- **User fields:** add them to user-service: a migration (`just migration …`), the `User` struct and its queries in `db.rs`, then `just sqlx-prepare`. To put a field in the JWT, add it to `Profile` (`models/user.rs`) and to the `claims` template in `oathkeeper.yml`. Only add a Kratos trait for a new *login identifier or recovery channel* (e.g. phone).
- **Roles:** add a variant to `models::Role` plus a migration updating the `user_roles.role` check constraint.
- **Login methods:** `selfservice.methods` in `kratos/kratos.yml`.
- **Email sender:** `courier.smtp` in `kratos.yml`. Mailpit catches everything locally.
- **Rotate the JWT key:** add a new key to `id_token.jwks.json` (Oathkeeper signs with the first key and publishes all of them). Remove the old one a few minutes later.

## Going to production (checklist)

1. **Same parent domain for everything, behind HTTPS.** For example: `myapp.com` (Oathkeeper → app), `auth.myapp.com` (Kratos public), `login.myapp.com` (UI). Set `cookies.domain` and `session.cookie.domain` to `myapp.com`.
2. Replace every `http://localhost:*` URL:
   - in `kratos.yml`;
   - in `oathkeeper.yml` (`issuer_url`, redirect `to`, and update your verifiers to match);
   - in the `access-rules.yml` match URLs;
   - in the compose env;
   - in `passkey.config.rp`;
   - in the OAuth callback URLs at Google/GitHub.
3. Remove `--dev` from the kratos command, and remove `DANGEROUSLY_DISABLE_SECURE_CSRF_COOKIES` from the UI.
4. Use a real SMTP provider (Resend, Postmark, SES, …) in `courier.smtp.connection_uri`.
5. Expose only Oathkeeper's proxy, the Kratos public API, and the UI. **Never** expose the Kratos admin API (4434), the Oathkeeper API (4456), Postgres, user-service, or your app directly. Remove the `127.0.0.1:5432` Postgres port mapping.
6. Remove `CREATEDB` from the `users` role in `postgres/create-users-db.sql` (only the tests need it).
7. Drop `mailpit`. Generate a fresh `.env` and JWT key per environment.
